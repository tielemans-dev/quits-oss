# Settlement provenance decision

Issue #32. Implementation candidate for parent review, 8 October 2026. This is a backend and contract change, not an approved production reconciliation design. It starts from money draft #72 at `295d00bbb856ec79c536e33888569a29592d52dc`. The parent owns publication and stack integration. Kvit UI work belongs to UX.

## Decision and existing behavior

Keep the money draft's `SettlementReceipt` as the cash record and `Payment.receiptId` as an allocation of that cash. Preserve its decimal arithmetic, explicit fees, two frozen FX quantities, remaining debt, allocation and refund corrections, and disabled discount/writeoff actions. Add source observations and explicit reconciliation decisions beside those records. Recording evidence itself changes neither cash nor debt.

The current source was inspected, including `domain/commands/settlements.ts`, `payments.ts`, `domain/execute.ts`, `domain/documents/settlement.ts`, the payments router, Prisma schema and migration, and the existing settlement DB tests. The draft's architecture document already describes original receipt evidence, unique organization references, actor attribution, and command idempotency. Provenance was not absent. The missing parts were source-event identity, separate reported/processing observations, reconciliation decisions, late-return composition and a read contract exposing attribution.

Runtime evidence has these meanings:

- `reported` records a claim. Client-source input is restricted to this state.
- `processing` records bank or provider processing evidence. It is not cash.
- `received` records source evidence that funds arrived. Recording it still creates no cash. An existing seller-confirmed receipt without bank/provider corroboration also has receipt provenance `received`.
- `verified` is a receipt's current human-reviewed match against compatible received bank/provider evidence. It does not mean Quits fetched the link, authenticated a bank statement, verified a webhook signature or guaranteed final settlement.
- `returned` source evidence retains an explicit reference to received evidence. Applying the separately previewed return reverses cash and its allocations. `returnPending` identifies a matched receipt that still needs that decision.

## Identity, arrival order and corrections

`SettlementEvidenceSource` identifies an organization, source kind, stable non-secret account reference and transaction reference. A source transaction can have only one current receipt. `SettlementEvidence` records immutable observations, source event IDs, source occurrence time, local recording time, operator actor key and command ID. `SettlementEvidenceDecision` retains matches, confirmations, unmatches, explicit mistaken-match rejections and applied returns. Source revisions order local decisions; they do not pretend to be the provider's event order.

The caller must retain the provider event ID or stable bank statement row ID across retries and imports. Duplicate IDs return the original observation across different actors and request IDs. Reusing an account-scoped event ID with changed facts or another transaction is refused. Distinct received events for the same source transaction may corroborate the same quantities but cannot create separate receipts. Account references cannot be import batch IDs. A future adapter must obtain stable account and transaction identities; this release has no feed or adapter.

A match names a receipt, an identity kind and value, a reason, and an evidence URL. Transaction/provider identity values must equal the supplied source transaction reference. A remittance-document identity permits an operator-reviewed cross-source reference. The operator is responsible for substantiating that identity; software does not decide it from amount and date. Exact currency, net and fee equality is an additional compatibility check, never sufficient identity proof. Different sources stay separate until a person explicitly links them.

Manual first: record one seller-confirmed receipt, then match compatible bank evidence to it. Bank first: record evidence, review `confirm`, create one receipt using the existing money command, and allocate that receipt. A later seller observation must use that existing receipt. The legacy free-form `recordReceipt` route does not infer identities from descriptions or dates and cannot prevent a person deliberately entering the same real-world money under unrelated references.

Unmatching removes corroboration, not cash, allocations or the established identity of that receipt. It retains the old match decision. A source that previously created or verified cash cannot use `confirm` to create cash again after unmatching. A cash correction requires reversing the prior receipt, explicitly correcting its evidence and reviewing a replacement. Source-created cash cannot be redirected to another active receipt. Corrections name the current received observation; old observations remain readable. SQL triggers reject updates to observations and decisions. The normal app has no provenance deletion command; restrictive foreign keys retain source history when deleting a customer, receipt or organization. Test cleanup deliberately deletes its own fixture history.

Replacement confirmation resolves the connected history of explicitly matched sources for the same customer. If bank A and provider B established one receipt, reversal and amount correction do not make them independent cash. The first replacement confirmation creates one receipt. The other source must match that replacement; its old confirmation preview is refused. Preview fingerprints include the related source revisions, established receipt links and receipt reversal state. Matching a different active receipt is also refused. No amount/date inference joins unrelated sources.

An accidental match can be withdrawn with `reject_match` after unmatching. It names the originally matched observation and receipt, requires `payment:void`, a reason and evidence, and appends an immutable decision. That source's earlier matches to that receipt stop establishing identity; other sources' links stay intact. A later explicit match can establish the link again. Source-created receipts cannot be detached this way, and returned source evidence cannot be reopened. Their financial corrections still require the money workflow. This separates withdrawal of a mistaken assertion from an ordinary unmatch and prevents an accidental old match becoming permanent identity.

Received evidence dominates earlier or later-arriving processing observations. Returned evidence is terminal for confirmation and verification. Reimporting or delivering an older received/processing event cannot reopen the same source as new cash. A return must reference received evidence from its own transaction. Missing causal evidence is refused for later retry rather than guessed.

## Returns, fees and FX

A full return previews the original net cash, fee and gross quantities, every active allocation, each invoice's current paid/credited/total quantities, current available funds and customer-credit classification. Commit recomputes that fingerprint under the organization lock. A stale financial or evidence decision fails before mutation.

If return evidence arrives before manual matching, the return preview can link it to an existing compatible receipt only with an explicit identity justification. A current link cannot be redirected by a return. After unmatching, the established corrected replacement remains the effective receipt for a justified return. `createdReceiptId` is creation attribution, not the return target selector; the prior creation and later match remain in immutable history.

The return composes the existing `reverse_allocation` handlers and `reverse_receipt` handler within one command transaction. Existing settlement events record each frozen reversal. The provenance decision links the return observation and the original receipt. Other receipts' allocations remain untouched. Original receipt amounts, evidence, payment rows and events remain. A late return restores invoice debt through the existing settlement calculation, including both original quantities for FX allocations.

Active refunds block a full return until an operator resolves them through the money correction workflow. This avoids inventing how a refund and a separate bank return relate. The command does not send money. Partial source returns, returns that retain a fee, aggregated payouts and automated reconciliation of old invoice-only payments need separately designed accounting treatment. They are refused or remain outside this workflow. Partial customer receipts, partial allocations, overpaid receipts and separately evidenced fees are supported. No base-currency valuation, fee VAT treatment, realized FX gain/loss, discount or writeoff policy is inferred.

Known legacy Stripe payment-intent/checkout identities on either `Invoice` or `Payment` are refused before materializing or matching another receipt, including the interval before the paid webhook creates a payment row. The existing webhook remains unchanged. Real-DB regressions compose the confirmation and `recordStripeCheckoutPayment` commands in both orders for session and intent references. These use synthetic system-command input, not a webhook HTTP request, signature verification or a live provider. Unknown references and account aliases are not inferred. This is not a complete legacy-payment adoption workflow, and callers must not record existing legacy payments again as unrelated receipts.

## Event and read integration

`settlement.evidence_recorded` and `settlement.evidence_decided`, version 1, carry durable source, observation and decision IDs plus their state/action and correction/reversal references. They enter the existing settlement CSV because it exports the `settlement.` event family. These are provenance metadata events, never additional cash, invoice revenue or debt postings. The immutable source/decision rows and authenticated history DTO supply the full references and operator justification. Financial movements continue to use the parent's existing receipt/allocation/change event payloads. Accounting adapters must skip or separately retain the metadata events; the current ledger posting policy is not extended.

The receipt read transaction takes the same organization lock as financial commands. Its balances, invoice debt, current attribution and correction history are one consistent read, including when a return commits concurrently. Return previews expose per-invoice debt before/after and receipt availability before/after, so clients do not have to calculate financial consequences.

## Collections and authorization

Processing guidance expires 72 hours after the earliest observed processing source timestamp for that source transaction. Reimports and newer processing events cannot extend it. Once expired, received or returned, it supplies no processing review deadline. `automaticCollectionSuppression` is always false. No reminder or collections code consumes the suggestion or pauses sending. The 72-hour limit is a conservative product choice for a review reminder, not an assertion about settlement speed or bank finality. A collections implementation would need a separate explicit, bounded policy and review before acting on it.

All entry points require authenticated organization permissions. Source entry and match/confirmation require `payment:create`; corrections, unmatching and returns also require `payment:void`. Accountants have read access under the existing role matrix. Agents and system actors cannot classify or confirm these observations. There is no new public customer mutation endpoint. Operators can record a customer report with its original source link and recorded actor attribution.

Handlers re-read membership while holding the membership row with `FOR SHARE`, under the existing organization transaction lock. Stale actor roles cannot authorize a write after revocation. Existing organization serialization covers matching versus allocations/refunds/returns. Router request IDs remain scoped by organization and actor through `executeCommand`; source-event deduplication also works across actors. Reuse a request ID only for an unchanged uncertain retry; changed decisions need new IDs, as in the parent money API.

## Source evidence and limits

Accessed 8 October 2026:

1. [Stripe webhook documentation, Event ordering and Handle duplicate events](https://docs.stripe.com/webhooks?locale=en-US#event-ordering) says delivery ordering is not guaranteed and repeated deliveries must be deduplicated by event ID. The [duplicate-events section](https://docs.stripe.com/webhooks?locale=en-US#handle-duplicate-events) also describes separate Event objects referring to the same underlying object. This supports retaining both source-event identity and transaction identity. It does not authorize treating a human-entered URL as a verified webhook.
2. [Stripe ACH Direct Debit, Timing and Disputes](https://docs.stripe.com/payments/ach-direct-debit#timing) distinguishes delayed confirmation from settlement. Its [disputes discussion](https://docs.stripe.com/payments/ach-direct-debit#disputes) describes rare late returns and the risk of a refund plus a bank dispute crediting the customer twice. This supports explicit reversal linkage and refusing unresolved refunds. It supplies no approved Danish tax or fee policy for this app.
3. [Upflow NetSuite late payment failure](https://docs.upflow.io/en-us/integrations/netsuite/late-payment-failure), introductory behavior and linked payment/refund examples, describes considering asynchronous payments successful by default and recording an offsetting refund on failure. That is contrary evidence to the conservative choice here: Quits does not confirm a reported/processing observation as cash by default. Upflow's choice establishes the problem, not the correct accounting policy for Quits.
4. [Money draft source at the pinned base](https://github.com/tielemans-dev/quits-oss/blob/295d00bbb856ec79c536e33888569a29592d52dc/apps/oss/src/domain/commands/settlements.ts), `recordReceipt`, `previewReceiptAllocation`, `previewReceiptChange` and `changeReceipt`, owns the existing arithmetic and correction behavior reused here. The [receipt architecture document](https://github.com/tielemans-dev/quits-oss/blob/295d00bbb856ec79c536e33888569a29592d52dc/docs/architecture/settlement-receipts.md) describes the accounting review boundary.

No interviews, accountant review, bank/provider pilot, live credentials or production reconciliation evidence were obtained. No provider accounts were registered and no external data was mutated. Discount/writeoff remains disabled. This implementation does not meet external evidence gaps by naming fixture runs as approvals. The dedicated Kvit handoff describes the deferred user-facing acceptance criterion.
